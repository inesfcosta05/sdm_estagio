99	Resumo
100	
101	
102	
103	Este relatório apresenta o trabalho realizado no âmbito do projeto de estágio intitulado "Migração e Reestruturação de Plataforma de Gestão de Contactos", desenvolvido na empresa Celeuma Multimédia Lda entre fevereiro e junho de 2026.
104	
105	O projeto consistiu na modernização de uma plataforma existente baseada em WordPress, transformando-a numa aplicação web robusta e escalável utilizando um stack tecnológico moderno: React.js para frontend, Node.js/Express para backend, e MySQL para persistência de dados. A solução integra dados tanto da aplicação local como do WordPress, mantendo sincronização automática e garantindo compatibilidade com dados históricos.
106	
107	O trabalho foi organizado em fases: análise da arquitetura existente, levantamento de requisitos, design da nova arquitetura, implementação de backend e frontend, sincronização com WordPress, testes e deployment em ambiente local e de produção.
108	
109	A solução final implementa funcionalidades completas para gestão de fichas comerciais, clientes, páginas, perfis de utilizador, administração de acessos e relatórios, com interface intuitiva e consistente que privilegia a produtividade. O sistema implementa mecanismos avançados de adaptação dinâmica ao schema da base de dados, normalização de dados, sincronização incremental com WordPress e configuração por variáveis de ambiente.
110	
111	Os resultados demonstram uma melhoria significativa em termos de manutenibilidade, escalabilidade, coerência visual-funcional e experiência do utilizador comparativamente à solução anterior.
112	
113	Palavras-chave: Migração de plataformas, WordPress, React.js, Node.js, Arquitetura web, API REST, Sincronização de dados, Base de dados MySQL

116	Abstract
117	
118	
119	
120	This report presents the work carried out within the scope of the internship project titled "Migration and Restructuring of Contact Management Platform", developed at Celeuma Multimédia Lda between fevereiro e junho de 2026.
121	
122	The project consisted of modernizing an existing WordPress-based platform, transforming it into a robust and scalable web application using modern technology stack: React.js for frontend, Node.js/Express for backend, and MySQL for data persistence. The solution integrates data from both the local application and WordPress, maintaining automatic synchronization and ensuring compatibility with historical data.
123	
124	The work was organized in phases: analysis of existing architecture, requirements gathering, design of new architecture, backend and frontend implementation, WordPress synchronization, testing and deployment in local and production environments.
125	
126	The final solution implements complete features for managing commercial records, clients, pages, user profiles, access administration and reports, with an intuitive and consistent interface that prioritizes productivity. The system implements advanced mechanisms for dynamic adaptation to database schema, data normalization, incremental synchronization with WordPress and environment-based configuration.
127	
128	Results demonstrate significant improvement in terms of maintainability, scalability, visual-functional consistency and user experience compared to the previous solution.
129	
130	Key-words: Platform migration, WordPress, React.js, Node.js, Web architecture, REST API, Data synchronization, MySQL database

179	Enquadramento e Contexto
180	O crescimento exponencial de informação nos sistemas de informação empresariais coloca desafios significativos em termos de organização, acessibilidade e manutenção. Muitas organizações, especialmente aquelas com histórico de evolução gradual de soluções tecnológicas, acabam por ter sistemas construídos em múltiplas tecnologias, com diferentes padrões de implementação e sem uma arquitetura coerente.
181	
182	A Celeuma Multimédia Lda, empresa especializada em soluções digitais e comunicação, contava com uma plataforma de gestão de contactos baseada em WordPress. Embora funcional, a solução apresentava limitações em termos de:
183	
184	•  Manutenibilidade: Código distribuído e difícil de manter
185	•  Escalabilidade: Dificuldades em suportar novas funcionalidades sem refatoração maior
186	•  Performance: Resposta lenta em operações complexas
187	•  Consistência: Interfaces e comportamentos inconsistentes entre módulos
188	•  Integração: Difícil comunicação entre o WordPress e sistemas auxiliares
189	
190	Neste contexto, foi identificada a necessidade de uma migração e reestruturação da plataforma, aproveitando stack tecnológico moderno que permitisse melhor separação de responsabilidades, maior flexibilidade e experiência de utilizador superior.

236	Plataformas de Gestão de Contactos
237	Plataformas de gestão de contactos (também designadas CRM - Customer Relationship Management - ou sistemas de gestão de relacionamento com clientes) são ferramentas críticas para organizações que necessitam de gerir grandes volumes de informação sobre clientes, propostas, transações e comunicações.
238	
239	Historicamente, estas plataformas evoluíram de sistemas monolíticos para arquiteturas distribuídas:
240	
241	•  Fase 1 (Sistemas Monolíticos): Aplicações tudo-em-um, tipicamente desktop
242	•  Fase 2 (Web Monolíticos): Aplicações web baseadas em templates server-side (PHP, ASP)
243	•  Fase 3 (Separação Frontend/Backend): API REST com frontend separado
244	•  Fase 4 (Microserviços e Cloud): Componentes independentes, escalabilidade horizontal
245	
246	A Celeuma operava entre as Fases 2 e 3, com WordPress (Fase 2) como base mas com necessidade clara de evoluir para Fase 3.

251	Arquiteturas Web Separadas por Camadas
252	A separação entre camadas (layered architecture) é um padrão amplamente aceito em engenharia de software que organiza a aplicação em:
253	
254	•  Camada de Apresentação (Frontend): Interface com o utilizador
255	•  Camada de Lógica de Negócio (Backend): Processamento, validação, regras
256	•  Camada de Persistência (Base de Dados): Armazenamento duradouro
257	
258	Vantagens:
259	•  Manutenção independente de cada camada
260	•  Reutilização da API por múltiplos clients
261	•  Escalabilidade horizontal
262	•  Facilita testes unitários e integração
263	•  Flexibilidade tecnológica
264	
265	Esta arquitetura foi o modelo escolhido para o projeto, com React.js no frontend, Node.js/Express no backend e MySQL na camada de dados.
266	Wordpress como plataforma de Conteúdos
267	WordPress é um Content Management System (CMS) muito popular, construído em PHP e MySQL. Inicialmente desenvolvido para blogging, evoluiu para plataforma robusta suportando:
268	
269	•  Extensão via plugins
270	•  Tipos de conteúdo customizados
271	•  REST API abrangente (desde versão 4.7)
272	•  Ecossistema vasto de temas e extensões
273	
274	No contexto deste projeto, WordPress funciona como:
275	•  Fonte de dados históricos: Dados de posts, clientes anteriores
276	•  Sistema de referência: Validação de dados sincronizados
277	•  Possível destino: Alguns dados criados localmente devem refletir em WordPress
278	
279	A integração com WordPress é complexa porque:
280	•  Schema não é fixo (customizado com plugins)
281	•  API tem limitações de autenticação e rate limiting
282	•  Dados podem estar em formatos variados
283	APIs REST e Integração entre Sistemas
284	REST (Representational State Transfer) é arquitetura para construir serviços web usando primitivos HTTP. Princípios:
285	
286	•  Identificadores de Recursos: URLs representam entidades (/fichas, /clientes)
287	•  Operações Padrão: GET (ler), POST (criar), PUT (atualizar), DELETE (eliminar)
288	•  Representações: Tipicamente JSON ou XML
289	•  Stateless: Cada requisição é independente
290	
291	No projeto, a API REST expõe:
292	•  Recursos principais: fichas, clientes, páginas, utilizadores
293	•  Operações CRUD completas
294	•  Filtros e paginação
295	•  Autenticação via tokens
296	
297	A separação frontend/backend via REST API permite:
298	•  Frontend focar em UI/UX
299	•  Backend focar em lógica de negócio
300	•  Fácil integração com outros sistemas
301	Frameworks Frontend Modernos
302	React.js (desenvolvido pelo Facebook) é biblioteca JavaScript para construir interfaces:
303	
304	•  Componentes: Blocos reutilizáveis de UI
305	•  Virtual DOM: Otimização de rendering
306	•  JSX: Sintaxe que mistura JavaScript com HTML-like markup
307	•  Hooks: Gerenciamento de estado e ciclo de vida
308	•  Ecossistema: React Router (routing), Axios (HTTP), Bootstrap (styling)
309	
310	React foi escolhido porque:
311	•  Comunidade grande e madura
312	•  Ferramentas excelentes (Create React App)
313	•  Componentes reutilizáveis simplificam desenvolvimento
314	•  Performance satisfatória para aplicações administrativas
315	•  Curva de aprendizagem razoável
316	Sincronização de Dados entre Sistemas
317	
318	Quando múltiplos sistemas armazenam dados relacionados, surge desafio de sincronização:
319	
320	•  Consistência Eventual: Dados sincronizam mas não instantaneamente
321	•  Incrementais vs. Completas: Sincronizar apenas mudanças ou tudo
322	•  Conflitos: Quando ambos os sistemas modificam o mesmo dado
323	•  Performance: Sincronização não deve bloquear operações normais
324	
325	Estratégias comuns:
326	•  Polling: Sistema verifica periodicamente por mudanças
327	•  Webhooks: Sistema receptor é notificado de mudanças
328	•  ETL: Extração, transformação, carregamento de dados
329	
330	O projeto utiliza polling com tracking de lastSync e incrementalidade com post_date_gmt.

332	Análise do Problema
333	
334	
335	Este capítulo analisa criticamente a plataforma de gestão de contactos que a Celeuma Multimédia Lda utilizava antes do projeto. Começa por descrever a situação inicial em termos de arquitetura e tecnologias (secção 3.1), identifica as principais fragilidades detetadas nessa solução (secção 3.2) e as oportunidades de melhoria que motivaram a migração (secção 3.3). A partir desta análise, são definidos os requisitos funcionais (secção 3.4) e não funcionais (secção 3.5) que orientaram o desenho da nova plataforma.
336	
337	Situação Inicial
338	A plataforma existente em Celeuma era baseada em WordPress com funcionalidades customizadas:
339	
340	•  Frontend: Temas customizados em PHP e JavaScript vanilla
341	•  Backend: WordPress plugins customizados
342	•  Base de Dados: MySQL com schema expandido via plugins
343	•  Dados: 6764 fichas, 4769 clientes, histórico de vários anos
344	
345	A plataforma era funcional mas apresentava vários problemas de manutenção:
346	
347	Plataforma Existente (WordPress)
348	├── Frontend
349	│   ├── Temas PHP customizados
350	│   ├── JavaScript vanilla (sem framework)
351	│   └── Interface inconsistente
352	├── Backend
353	│   ├── Plugins WordPress
354	│   ├── Lógica espalhada por hooks
355	│   └── Difícil de testar
356	└── Base de Dados
357	    ├── Schema heterogéneo
358	    ├── Dados duplicados
359	    └── Campos órfãos

362	Fragilidades Identificadas
363	
364	Fragilidade 1: Acoplamento Frontend-Backend
365	WordPress mistura apresentação e lógica, dificultando testes e reutilização de código.
366	
367	Fragilidade 2: Performance
368	Renderização server-side para cada página causa latência perceptível ao utilizador.
369	
370	Fragilidade 3: Escalabilidade
371	Adicionar novas funcionalidades requer modificação de múltiplos ficheiros espalhados.
372	
373	Fragilidade 4: Consistência de Interface
374	Diferentes módulos tinham estilos e comportamentos inconsistentes.
375	
376	Fragilidade 5: Dados Heterogéneos
377	Campos opcionais ou mal estruturados causavam erros frequentes.
378	
379	Fragilidade 6: Manutenibilidade do Código
380	Documentação insuficiente, código legado com múltiplos autores.
381	
382	Oportunidades de Melhoria
383	1. Modernização Tecnológica
384	•  React no frontend para componentes reutilizáveis e performance
385	•  Node.js no backend para código mais limpo e testável
386	
387	2. Separação de Responsabilidades
388	•  Frontend focado exclusivamente em UI/UX
389	•  Backend focado em lógica, validação, persistência
390	
391	3. Consistência de Interface
392	•  Design system único
393	•  Componentes reutilizáveis
394	•  Tema dinâmico
395	
396	4. Robustez de Dados
397	•  Validação em múltiplas camadas
398	•  Normalização automática
399	•  Schema dinâmico adaptável
400	
401	5. Extensibilidade
402	•  API REST bem documentada
403	•  Fácil adicionar novos endpoints
404	•  Possibilidade de múltiplos clientes (web, mobile, etc.)

886	Entidade Fichas
887	
888	A tabela fichas é o core da aplicação e guarda o registo comercial completo de cada contacto/proposta. O script backend/schema.sql inclui apenas uma tabela de arranque simplificada; a tabela em produção segue antes a nomenclatura de campos herdada do WordPress (definida em getFichaColumnValueMap(), server.js), com informação de:
889	
890	•  Identificação: id, legacy_id (referência ao post original no WordPress), title
891	•  Classificação: post_status, post_visibility
892	•  Relacionamentos: author, client_legacy_id
893	•  Financeiro: valor_total_proposta, valor_total_adjudicado, valor_fatura, data_fatura
894	•  Comercial: tipo_contacto, data_apresentacao_proposta, estado_proposta, servicos_adjudicados
895	•  Datas: post_date, data_contacto, data_ultimo_contacto_financeiro
896	
897	Particularidades:
898	•  Schema com muitos campos opcionais: nem todos os registos preenchem todos os campos
899	•  Compatibilidade: legacy_id permite rastrear dados antigos
900	•  Auditoria: relatorio_errado / porque_relatorio_errado assinalam registos com dados a rever
901	
902	Entidade Clientes
903	
904	A tabela chama-se clients (não clientes) e guarda dados de organizações/pessoas:
905	
906	•  Identificação: id, legacy_id, denominacao_fiscal, nif
907	•  Contacto: contacto_empresa, pessoa_contacto_nome, pessoa_contacto_cargo, pessoa_contacto_telefone_email
908	•  Localização: morada
909	•  Estado: estado, visibilidade, senha_visibilidade
910	•  Relacionamento: comercial_id (gestor responsável), author
911	
912	Deduplicação: o script dedupe.js remove duplicados por legacy_id e garante um índice único nesse campo
913	
914	Entidade Páginas
915	
916	Tabela wp_posts com conteúdo editorial:
917	
918	•  Conteúdo: post_title, post_content, post_excerpt
919	•  Metadados: post_status, post_type, post_date_gmt
920	•  Estrutura: post_parent (para hierarchia), menu_order
921	•  Autoria: post_author, post_modified_gmt
922	
923	Nota: Pode estar em WordPress remoto ou localmente

1026	const normalizeUserRole = (role) => {
1027	  const raw = (role || '').toString().trim().toLowerCase();
1028	  if (raw === 'administrator' || raw === 'administrador') return 'admin';
1029	  if (raw === 'admin') return 'admin';
1030	  if (raw === 'contribuidor' || raw === 'contributor') return 'contributor';
1031	  if (raw === 'editor' || raw === 'editora') return 'editor';
1032	  return raw || 'editor';
1033	};

1182	function FormBuilder({ schema, initialValues, onSubmit }) {
1183	  const [values, setValues] = useState(initialValues);
1184	  const [errors, setErrors] = useState({});
1185	
1186	  const handleChange = (e) => {
1187	    const { name, value } = e.target;
1188	    setValues(prev => ({ ...prev, [name]: value }));
1189	  };
1190	
1191	  const handleSubmit = async (e) => {
1192	    e.preventDefault();
1193	    try {
1194	      await onSubmit(values);
1195	    } catch (err) {
1196	      setErrors(err.response.data.errors);
1197	    }
1198	  };
1199	
1200	  return (
1201	    <form onSubmit={handleSubmit}>
1202	      {schema.map(field => (
1203	        <div key={field.name} className="mb-3">
1204	          <label>{field.label}</label>
1205	          <input
1206	            type={field.type}
1207	            name={field.name}
1208	            value={values[field.name] || ''}
1209	            onChange={handleChange}
1210	            required={field.required}
1211	            className={errors[field.name] ? 'is-invalid' : ''}
1212	          />
1213	          {errors[field.name] && <span className="error">{errors[field.name]}</span>}
1214	        </div>
1215	      ))}
1216	      <button type="submit">Guardar</button>
1217	    </form>
1218	  );
1219	}

1419	Sincronização com WordPress
1420	
1421	Justificação da Integração
1422	
1423	O WordPress funciona como fonte de dados históricos porque:
1424	•  Muitos registos foram criados em WordPress originalmente
1425	•  Alguns utilizadores ainda editam dados lá
1426	•  Desejamos manter compatibilidade
1427	•  Gradualmente migrar dados (não tudo de uma vez)
1428	
1429	A sincronização garante que a aplicação local fica sempre atualizada.
1430	
1431	Serviço de Sincronização
1432	
1433	O sync-service.js executa a cada 5 minutos:
1434	
1435	// sync-service.js
1436	class SyncService {
1437	  start() {
1438	    this.interval = setInterval(() => this.sync(), 5 * 60 * 1000); // 5 min
1439	  }
1440	
1441	  async sync() {
1442	    try {
1443	      await this.syncFichas();
1444	      await this.syncClients();
1445	      await this.syncPages();
1446	      
1447	      // Guardar lastSync para próxima execução
1448	      this.lastSync = new Date();
1449	    } catch (error) {
1450	      console.error('Sync error:', error);
1451	    }
1452	  }
1453	
1454	  async syncFichas() {
1455	    // Fetch completo (sempre todas as páginas, não filtrado por data)
1456	    const fichas = await this.fetchWordPressCollection('fichas');
1457	    
1458	    for (const ficha of fichas) {
1459	      // Normalizar dados
1460	      const normalized = this.normalizeFicha(ficha);
1461	      
1462	      // Inserir ou atualizar
1463	      await pool.query(`
1464	        INSERT INTO fichas (legacy_id, titulo, descricao, ...)
1465	        VALUES (?, ?, ?, ...)
1466	        ON DUPLICATE KEY UPDATE
1467	        titulo = VALUES(titulo),
1468	        descricao = VALUES(descricao),
1469	        ...
1470	      `, [ficha.legacy_id, normalized.titulo, ...]);
1471	    }
1472	  }
1473	
1474	  async fetchWordPressCollection(collection) {
1475	    const results = [];
1476	    let page = 1;
1477	
1478	    while (true) {
1479	      const response = await wpClient.get(/wp-json/wp/v2/${collection}?per_page=100&page=${page});
1480	      if (response.data.length === 0) break;
1481	      
1482	      results.push(...response.data);
1483	      page++;
1484	    }
1485	
1486	    return results;
1487	  }
1488	}
1489	
1490	// Iniciar ao launch do servidor
1491	const syncService = new SyncService();
1492	syncService.start();

1494	Estratégia de Sincronização
1495	
1496	Apesar do nome lastSync, a sincronização não é incremental: cada ciclo de 5 minutos faz sempre um fetch completo de todas as coleções (fichas, clients, pages, users), paginado de 100 em 100 registos, e depois apaga localmente os registos que já não existem no WordPress ("orphan cleanup"). O campo lastSync serve apenas para reporte de estado em GET /api/sync/status, não para filtrar o pedido ao WordPress.
1497	
1498	async syncFichas() {
1499	  const remoteItems = await this.fetchWordPressCollection('fichas'); // fetch completo, sempre
1500	
1501	  for (const item of remoteItems) {
1502	    await this.upsertLocalFicha(item);
1503	  }
1504	
1505	  // remove localmente o que já não existe no WordPress
1506	  await this.deleteOrphans('fichas', remoteItems.map(r => r.id));
1507	
1508	  this.lastSync = new Date(); // só para reporte de estado, não filtra o próximo fetch
1509	}
1510	
1511	Não há tratamento diferenciado por tipo de erro (401, timeout, etc.): qualquer falha é capturada, o erro é registado em log e o ciclo simplesmente tenta de novo passados 5 minutos, sem lógica de retry dentro do próprio ciclo.
1512	Tratamento de Erros
1513	
1514	async getFromWordPressResponse(url) {
1515	  try {
1516	    const response = await wpClient.get(url);
1517	    return { status: response.status, data: response.data };
1518	  } catch (error) {
1519	    console.error('Sync error:', error.message);
1520	    return { status: 0, data: null };
1521	  }
1522	}

1762	const fieldAliases = {

1771	function normalizeState(value) {
1772	  const stateMap = {
1773	    'draft': 'draft',

1780	    'arquivado': 'archive',

1786	// Schema dinâmico
1787	async function getFichaColumnValueMap(req) {
1788	  const [columns] = await pool.query('DESCRIBE fichas');
1789	  const validColumns = columns.map(c => c.Field);
1790	  
1791	  const updates = {};

1793	    const actualColumn = fieldAliases[key] || key;
1794	    if (validColumns.includes(actualColumn)) {
1795	      updates[actualColumn] = value;
1796	    }
1797	  }
1798	  return updates;

1829	Sincronização com Estados Inesperados
1830	
1831	Problema: WordPress API às vezes retorna dados incompletos ou inesperados (HTTP 400, timeout).
1832	
1833	Erros observados:
1834	400 Bad Request - campos faltam
1835	401 Unauthorized - credenciais expiradas  
1836	429 Too Many Requests - rate limiting
1837	504 Gateway Timeout - WordPress offline
1838	
1839	Solução Implementada:
1840	
1841	async function syncWithRetry(maxRetries = 3) {
1842	  for (let attempt = 1; attempt <= maxRetries; attempt++) {
1843	    try {
1844	      const fichas = await wpClient.get('/wp-json/wp/v2/fichas');
1845	      return fichas.data;
1846	    } catch (error) {
1847	      console.warn(Tentativa ${attempt} falhou:, error.message);
1848	      
1849	      if (error.response?.status === 401) {
1850	        console.error('Credenciais WordPress inválidas - sincronização desativada');
1851	        return [];
1852	      }
1853	      
1854	      if (attempt < maxRetries) {
1855	        const waitTime = Math.pow(2, attempt) * 1000; // Exponential backoff
1856	        console.log(Aguardando ${waitTime}ms antes de repetir...);
1857	        await new Promise(r => setTimeout(r, waitTime));
1858	      }
1859	    }
1860	  }
1861	  
1862	  console.error('Sincronização falhou após todas as tentativas');
1863	  return [];
1864	}
1865	
1866	Resultado: Sistema é resiliente a falhas temporárias de WordPress.

1879	// backend/scripts/ensure_unique_indexes.js
1880	async function ensureUniqueIndexes() {
1881	  // Remover duplicados por legacy_id
1882	  await pool.query(`
1883	    DELETE t1 FROM fichas t1
1884	    INNER JOIN fichas t2
1885	    WHERE t1.id > t2.id
1886	    AND t1.legacy_id = t2.legacy_id
1887	    AND t1.legacy_id IS NOT NULL
1888	  `);
1889	
1890	  // Remover duplicados de clientes por NIF
1891	  await pool.query(`
1892	    DELETE t1 FROM clientes t1
1893	    INNER JOIN clientes t2
1894	    WHERE t1.id > t2.id
1895	    AND t1.nif = t2.nif
1896	    AND t1.nif IS NOT NULL
1897	  `);
1898	
1899	  console.log('✓ Duplicados removidos');
1900	}

1902	// Validar e corrigir estados inválidos
1903	async function fixInvalidStates() {
1904	  const validStates = ['draft', 'publish', 'archive'];
1905	  
1906	  const [invalid] = await pool.query(`
1907	    SELECT id, post_status FROM fichas
1908	    WHERE post_status NOT IN (?, ?, ?)
1909	  `, validStates);
1910	
1911	  for (const row of invalid) {
1912	    await pool.query(
1913	      'UPDATE fichas SET post_status = ? WHERE id = ?',
1914	      ['draft', row.id]
1915	    );
1916	  }
1917	
1918	  console.log(✓ ${invalid.length} estados corrigidos);
1919	}
