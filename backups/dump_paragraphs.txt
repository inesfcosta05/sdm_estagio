104	Normal	Este relatório apresenta o trabalho realizado no âmbito do projeto de estágio intitulado "Migração e Reestruturação de Plataforma de Gestão de Contactos", desenvolvido na empresa Celeuma Multimédia Lda entre fevereiro e junho de 2026.
105	Normal	
106	Normal	O projeto consistiu na modernização de uma plataforma existente baseada em WordPress, transformando-a numa aplicação web robusta e escalável utilizando um stack tecnológico moderno: React.js para frontend, Node.js/Express para backend, e MySQL para persistência de dados. A solução integra dados tanto da aplicação local como do WordPress, mantendo sincronização automática e garantindo compatibilidade com dados históricos.
107	Normal	
108	Normal	O trabalho foi organizado em fases: análise da arquitetura existente, levantamento de requisitos, design da nova arquitetura, implementação de backend e frontend, sincronização com WordPress, testes e deployment em ambiente local e de produção.
109	Normal	
110	Normal	A solução final implementa funcionalidades completas para gestão de fichas comerciais, clientes, páginas, perfis de utilizador, administração de acessos e relatórios, com interface intuitiva e consistente que privilegia a produtividade. O sistema implementa mecanismos avançados de adaptação dinâmica ao schema da base de dados, normalização de dados, sincronização incremental com WordPress e configuração por variáveis de ambiente.
111	Normal	
112	Normal	Os resultados demonstram uma melhoria significativa em termos de manutenibilidade, escalabilidade, coerência visual-funcional e experiência do utilizador comparativamente à solução anterior.
113	Normal

121	Normal	This report presents the work carried out within the scope of the internship project titled "Migration and Restructuring of Contact Management Platform", developed at Celeuma Multimédia Lda between fevereiro e junho de 2026.
122	Normal	
123	Normal	The project consisted of modernizing an existing WordPress-based platform, transforming it into a robust and scalable web application using modern technology stack: React.js for frontend, Node.js/Express for backend, and MySQL for data persistence. The solution integrates data from both the local application and WordPress, maintaining automatic synchronization and ensuring compatibility with historical data.
124	Normal	
125	Normal	The work was organized in phases: analysis of existing architecture, requirements gathering, design of new architecture, backend and frontend implementation, WordPress synchronization, testing and deployment in local and production environments.
126	Normal	
127	Normal	The final solution implements complete features for managing commercial records, clients, pages, user profiles, access administration and reports, with an intuitive and consistent interface that prioritizes productivity. The system implements advanced mechanisms for dynamic adaptation to database schema, data normalization, incremental synchronization with WordPress and environment-based configuration.
128	Normal	
129	Normal	Results demonstrate significant improvement in terms of maintainability, scalability, visual-functional consistency and user experience compared to the previous solution.

274	Heading 2	Arquiteturas Web Separadas por Camadas
275	Body Text	A separação entre camadas (layered architecture) é um padrão amplamente aceito em engenharia de software que organiza a aplicação em:
276	Body Text	
277	Body Text	- **Camada de Apresentação (Frontend):** Interface com o utilizador
278	Body Text	- **Camada de Lógica de Negócio (Backend):** Processamento, validação, regras
279	Body Text	- **Camada de Persistência (Base de Dados):** Armazenamento duradouro
280	Body Text	
281	Body Text	**Vantagens:**
282	Body Text	- Manutenção independente de cada camada
283	Body Text	- Reutilização da API por múltiplos clients
284	Body Text	- Escalabilidade horizontal
285	Body Text	- Facilita testes unitários e integração
286	Body Text	- Flexibilidade tecnológica
287	Body Text	
288	Body Text	Esta arquitetura foi o modelo escolhido para o projeto, com React.js no frontend, Node.js/Express no backend e MySQL na camada de dados.

297	Body Text	
298	Body Text	No contexto deste projeto, WordPress funciona como:

301	Body Text	- **Possível destino:** Alguns dados criados localmente devem refletir em WordPress

304	Body Text	- Schema não é fixo (customizado com plugins)
305	Body Text	- API tem limitações de autenticação e rate limiting
306	Body Text	- Dados podem estar em formatos variados
307	Heading 2	2.4 APIs REST e Integração entre Sistemas
308	Body Text	REST (Representational State Transfer) é arquitetura para construir serviços web usando primitivos HTTP. Princípios:
309	Body Text	
310	Body Text	- **Identificadores de Recursos:** URLs representam entidades (/fichas, /clientes)
311	Body Text	- **Operações Padrão:** GET (ler), POST (criar), PUT (atualizar), DELETE (eliminar)
312	Body Text	- **Representações:** Tipicamente JSON ou XML
313	Body Text	- **Stateless:** Cada requisição é independente
314	Body Text	
315	Body Text	No projeto, a API REST expõe:
316	Body Text	- Recursos principais: fichas, clientes, páginas, utilizadores
317	Body Text	- Operações CRUD completas
318	Body Text	- Filtros e paginação
319	Body Text	- Autenticação via tokens
320	Body Text	
321	Body Text	A separação frontend/backend via REST API permite:
322	Body Text	- Frontend focar em UI/UX
323	Body Text	- Backend focar em lógica de negócio
324	Body Text	- Fácil integração com outros sistemas
325	Heading 2	2.5 Frameworks Frontend Modernos

327	Body Text	
328	Body Text	- **Componentes:** Blocos reutilizáveis de UI
329	Body Text	- **Virtual DOM:** Otimização de rendering
330	Body Text	- **JSX:** Sintaxe que mistura JavaScript com HTML-like markup
331	Body Text	- **Hooks:** Gerenciamento de estado e ciclo de vida
332	Body Text	- **Ecossistema:** React Router (routing), Axios (HTTP), Bootstrap (styling)
333	Body Text	
334	Body Text	React foi escolhido porque:
335	Body Text	- Comunidade grande e madura
336	Body Text	- Ferramentas excelentes (Create React App)

338	Body Text	- Performance satisfatória para aplicações administrativas

340	Heading 2	2.6 Sincronização de Dados entre Sistemas
341	Body Text	
342	Body Text	Quando múltiplos sistemas armazenam dados relacionados, surge desafio de sincronização:
343	Body Text	
344	Body Text	- **Consistência Eventual:** Dados sincronizam mas não instantaneamente
345	Body Text	- **Incrementais vs. Completas:** Sincronizar apenas mudanças ou tudo
346	Body Text	- **Conflitos:** Quando ambos os sistemas modificam o mesmo dado
347	Body Text	- **Performance:** Sincronização não deve bloquear operações normais
348	Body Text	
349	Body Text	Estratégias comuns:
350	Body Text	- **Polling:** Sistema verifica periodicamente por mudanças
351	Body Text	- **Webhooks:** Sistema receptor é notificado de mudanças
352	Body Text	- **ETL:** Extração, transformação, carregamento de dados

1590	Heading 2	11.1. Justificação da Integração
1591	Body Text	
1592	Body Text	O WordPress funciona como fonte de dados históricos porque:

1594	Body Text	- Alguns utilizadores ainda editam dados lá

1600	Heading 2	11.2. Serviço de Sincronização
1601	Body Text	
1602	Body Text	O `sync-service.js` executa a cada 5 minutos:
1603	Body Text	
1604	Body Text	```javascript
1605	Body Text	// sync-service.js
1606	Body Text	class SyncService {
1607	Body Text	  start() {
1608	Body Text	    this.interval = setInterval(() => this.sync(), 5 * 60 * 1000); // 5 min
1609	Body Text	  }
1610	Body Text	
1611	Body Text	  async sync() {
1612	Body Text	    try {
1613	Body Text	      await this.syncFichas();
1614	Body Text	      await this.syncClients();
1615	Body Text	      await this.syncPages();
1616	Body Text	      
1617	Body Text	      // Guardar lastSync para próxima execução
1618	Body Text	      this.lastSync = new Date();
1619	Body Text	    } catch (error) {
1620	Body Text	      console.error('Sync error:', error);
1621	Body Text	    }
1622	Body Text	  }
1623	Body Text	
1624	Body Text	  async syncFichas() {
1625	Body Text	    // Obter fichas modificadas desde lastSync
1626	Body Text	    const fichas = await this.fetchWordPressCollection('fichas');
1627	Body Text	    
1628	Body Text	    for (const ficha of fichas) {
1629	Body Text	      // Normalizar dados
1630	Body Text	      const normalized = this.normalizeFicha(ficha);
1631	Body Text	      
1632	Body Text	      // Inserir ou atualizar
1633	Body Text	      await pool.query(`
1634	Body Text	        INSERT INTO fichas (legacy_id, titulo, descricao, ...)
1635	Body Text	        VALUES (?, ?, ?, ...)
1636	Body Text	        ON DUPLICATE KEY UPDATE
1637	Body Text	        titulo = VALUES(titulo),
1638	Body Text	        descricao = VALUES(descricao),
1639	Body Text	        ...
1640	Body Text	      `, [ficha.legacy_id, normalized.titulo, ...]);
1641	Body Text	    }
1642	Body Text	  }
1643	Body Text	
1644	Body Text	  async fetchWordPressCollection(collection) {
1645	Body Text	    const results = [];
1646	Body Text	    let page = 1;
1647	Body Text	
1648	Body Text	    while (true) {
1649	Body Text	      const response = await wpClient.get(`/wp-json/wp/v2/${collection}?per_page=100&page=${page}`);
1650	Body Text	      if (response.data.length === 0) break;
1651	Body Text	      
1652	Body Text	      results.push(...response.data);
1653	Body Text	      page++;
1654	Body Text	    }
1655	Body Text	
1656	Body Text	    return results;
1657	Body Text	  }
1658	Body Text	}
1659	Body Text	
1660	Body Text	// Iniciar ao launch do servidor
1661	Body Text	const syncService = new SyncService();
1662	Body Text	syncService.start();
1663	Body Text	```

1968	Body Text	
1969	Body Text	**Problema:** Dados históricos tem campos em diferentes formatos/nomes.

1974	Body Text	- Booleanos: 1/0 vs "true"/"false" vs "on"/"off"
1975	Body Text	
1976	Body Text	**Solução Implementada:**
1977	Body Text	
1978	Body Text	```javascript
1979	Body Text	// Mapeamento de nomes de campo alternativos
1980	Body Text	const fieldAliases = {
1981	Body Text	  'data_proposta': 'proposal_date',
1982	Body Text	  'data_proposta_alt': 'proposal_date',
1983	Body Text	  'data': 'proposal_date',
1984	Body Text	  'estado': 'post_status',

2054	Heading 2	14.3. Sincronização com Estados Inesperados
2055	Body Text	
2056	Body Text	**Problema:** WordPress API às vezes retorna dados incompletos ou inesperados (HTTP 400, timeout).
2057	Body Text	
2058	Body Text	**Erros observados:**
2059	Body Text	```
2060	Body Text	400 Bad Request - campos faltam
2061	Body Text	401 Unauthorized - credenciais expiradas  
2062	Body Text	429 Too Many Requests - rate limiting
2063	Body Text	504 Gateway Timeout - WordPress offline
2064	Body Text	```
2065	Body Text	
2066	Body Text	**Solução Implementada:**
2067	Body Text	
2068	Body Text	```javascript
2069	Body Text	async function syncWithRetry(maxRetries = 3) {
2070	Body Text	  for (let attempt = 1; attempt <= maxRetries; attempt++) {
2071	Body Text	    try {
2072	Body Text	      const fichas = await wpClient.get('/wp-json/wp/v2/fichas');
2073	Body Text	      return fichas.data;
2074	Body Text	    } catch (error) {
2075	Body Text	      console.warn(`Tentativa ${attempt} falhou:`, error.message);
2076	Body Text	      
2077	Body Text	      if (error.response?.status === 401) {
2078	Body Text	        console.error('Credenciais WordPress inválidas - sincronização desativada');
2079	Body Text	        return [];
2080	Body Text	      }
2081	Body Text	      
2082	Body Text	      if (attempt < maxRetries) {
2083	Body Text	        const waitTime = Math.pow(2, attempt) * 1000; // Exponential backoff
2084	Body Text	        console.log(`Aguardando ${waitTime}ms antes de repetir...`);
2085	Body Text	        await new Promise(r => setTimeout(r, waitTime));
2086	Body Text	      }
2087	Body Text	    }
2088	Body Text	  }
2089	Body Text	  
2090	Body Text	  console.error('Sincronização falhou após todas as tentativas');
2091	Body Text	  return [];
2092	Body Text	}
2093	Body Text	```
2094	Body Text	
2095	Body Text	**Resultado:** Sistema é resiliente a falhas temporárias de WordPress.
