103	Normal	Este relatório apresenta o trabalho realizado no âmbito do projeto de estágio intitulado "Migração e Reestruturação de Plataforma de Gestão de Contactos", desenvolvido na empresa Celeuma Multimédia Lda entre fevereiro e junho de 2026.
104	Normal	
105	Normal	O projeto consistiu na modernização de uma plataforma existente baseada em WordPress, transformando-a numa aplicação web robusta e escalável utilizando um stack tecnológico moderno: React.js para frontend, Node.js/Express para backend, e MySQL para persistência de dados. A solução integra dados tanto da aplicação local como do WordPress, mantendo sincronização automática e garantindo compatibilidade com dados históricos.
106	Normal	
107	Normal	O trabalho foi organizado em fases: análise da arquitetura existente, levantamento de requisitos, design da nova arquitetura, implementação de backend e frontend, sincronização com WordPress, testes e deployment em ambiente local e de produção.
108	Normal	
109	Normal	A solução final implementa funcionalidades completas para gestão de fichas comerciais, clientes, páginas, perfis de utilizador, administração de acessos e relatórios, com interface intuitiva e consistente que privilegia a produtividade. O sistema implementa mecanismos avançados de adaptação dinâmica ao schema da base de dados, normalização de dados, sincronização incremental com WordPress e configuração por variáveis de ambiente.
110	Normal	
111	Normal	Os resultados demonstram uma melhoria significativa em termos de manutenibilidade, escalabilidade, coerência visual-funcional e experiência do utilizador comparativamente à solução anterior.
112	Normal	
113	Normal	Palavras-chave: Migração de plataformas, WordPress, React.js, Node.js, Arquitetura web, API REST, Sincronização de dados, Base de dados MySQL

120	Normal	This report presents the work carried out within the scope of the internship project titled "Migration and Restructuring of Contact Management Platform", developed at Celeuma Multimédia Lda between fevereiro e junho de 2026.
121	Normal	
122	Normal	The project consisted of modernizing an existing WordPress-based platform, transforming it into a robust and scalable web application using modern technology stack: React.js for frontend, Node.js/Express for backend, and MySQL for data persistence. The solution integrates data from both the local application and WordPress, maintaining automatic synchronization and ensuring compatibility with historical data.
123	Normal	
124	Normal	The work was organized in phases: analysis of existing architecture, requirements gathering, design of new architecture, backend and frontend implementation, WordPress synchronization, testing and deployment in local and production environments.
125	Normal	
126	Normal	The final solution implements complete features for managing commercial records, clients, pages, user profiles, access administration and reports, with an intuitive and consistent interface that prioritizes productivity. The system implements advanced mechanisms for dynamic adaptation to database schema, data normalization, incremental synchronization with WordPress and environment-based configuration.
127	Normal	
128	Normal	Results demonstrate significant improvement in terms of maintainability, scalability, visual-functional consistency and user experience compared to the previous solution.
129	Normal	
130	Normal	Key-words: Platform migration, WordPress, React.js, Node.js, Web architecture, REST API, Data synchronization, MySQL database

255	Body Text	Plataformas de gestão de contactos (também designadas CRM - Customer Relationship Management - ou sistemas de gestão de relacionamento com clientes) são ferramentas críticas para organizações que necessitam de gerir grandes volumes de informação sobre clientes, propostas, transações e comunicações.

261	Body Text	•  Fase 3 (Separação Frontend/Backend): API REST com frontend separado
262	Body Text	•  Fase 4 (Microserviços e Cloud): Componentes independentes, escalabilidade horizontal
263	Body Text	
264	Body Text	A Celeuma operava entre as Fases 2 e 3, com WordPress (Fase 2) como base mas com necessidade clara de evoluir para Fase 3.

269	Heading 2	Arquiteturas Web Separadas por Camadas
270	Body Text	A separação entre camadas (layered architecture) é um padrão amplamente aceito em engenharia de software que organiza a aplicação em:
271	Body Text	
272	Body Text	•  Camada de Apresentação (Frontend): Interface com o utilizador
273	Body Text	•  Camada de Lógica de Negócio (Backend): Processamento, validação, regras
274	Body Text	•  Camada de Persistência (Base de Dados): Armazenamento duradouro
275	Body Text	
276	Body Text	Vantagens:
277	Body Text	•  Manutenção independente de cada camada
278	Body Text	•  Reutilização da API por múltiplos clients
279	Body Text	•  Escalabilidade horizontal
280	Body Text	•  Facilita testes unitários e integração
281	Body Text	•  Flexibilidade tecnológica
282	Body Text	
283	Body Text	Esta arquitetura foi o modelo escolhido para o projeto, com React.js no frontend, Node.js/Express no backend e MySQL na camada de dados.
284	Heading 2	Wordpress como plataforma de Conteúdos
285	Body Text	WordPress é um Content Management System (CMS) muito popular, construído em PHP e MySQL. Inicialmente desenvolvido para blogging, evoluiu para plataforma robusta suportando:
286	Body Text	
287	Body Text	•  Extensão via plugins
288	Body Text	•  Tipos de conteúdo customizados
289	Body Text	•  REST API abrangente (desde versão 4.7)
290	Body Text	•  Ecossistema vasto de temas e extensões
291	Body Text	
292	Body Text	No contexto deste projeto, WordPress funciona como:
293	Body Text	•  Fonte de dados históricos: Dados de posts, clientes anteriores
294	Body Text	•  Sistema de referência: Validação de dados sincronizados
295	Body Text	•  Possível destino: Alguns dados criados localmente devem refletir em WordPress
296	Body Text	
297	Body Text	A integração com WordPress é complexa porque:
298	Body Text	•  Schema não é fixo (customizado com plugins)
299	Body Text	•  API tem limitações de autenticação e rate limiting
300	Body Text	•  Dados podem estar em formatos variados
301	Heading 2	APIs REST e Integração entre Sistemas
302	Body Text	REST (Representational State Transfer) é arquitetura para construir serviços web usando primitivos HTTP. Princípios:
303	Body Text	
304	Body Text	•  Identificadores de Recursos: URLs representam entidades (/fichas, /clientes)
305	Body Text	•  Operações Padrão: GET (ler), POST (criar), PUT (atualizar), DELETE (eliminar)
306	Body Text	•  Representações: Tipicamente JSON ou XML
307	Body Text	•  Stateless: Cada requisição é independente
308	Body Text	
309	Body Text	No projeto, a API REST expõe:
310	Body Text	•  Recursos principais: fichas, clientes, páginas, utilizadores
311	Body Text	•  Operações CRUD completas
312	Body Text	•  Filtros e paginação
313	Body Text	•  Autenticação via tokens
314	Body Text	
315	Body Text	A separação frontend/backend via REST API permite:
316	Body Text	•  Frontend focar em UI/UX
317	Body Text	•  Backend focar em lógica de negócio
318	Body Text	•  Fácil integração com outros sistemas
319	Heading 2	Frameworks Frontend Modernos
320	Body Text	React.js (desenvolvido pelo Facebook) é biblioteca JavaScript para construir interfaces:
321	Body Text	
322	Body Text	•  Componentes: Blocos reutilizáveis de UI
323	Body Text	•  Virtual DOM: Otimização de rendering
324	Body Text	•  JSX: Sintaxe que mistura JavaScript com HTML-like markup
325	Body Text	•  Hooks: Gerenciamento de estado e ciclo de vida
326	Body Text	•  Ecossistema: React Router (routing), Axios (HTTP), Bootstrap (styling)
327	Body Text	
328	Body Text	React foi escolhido porque:
329	Body Text	•  Comunidade grande e madura
330	Body Text	•  Ferramentas excelentes (Create React App)
331	Body Text	•  Componentes reutilizáveis simplificam desenvolvimento
332	Body Text	•  Performance satisfatória para aplicações administrativas
333	Body Text	•  Curva de aprendizagem razoável
334	Heading 2	Sincronização de Dados entre Sistemas
335	Body Text	
336	Body Text	Quando múltiplos sistemas armazenam dados relacionados, surge desafio de sincronização:
337	Body Text	
338	Body Text	•  Consistência Eventual: Dados sincronizam mas não instantaneamente
339	Body Text	•  Incrementais vs. Completas: Sincronizar apenas mudanças ou tudo
340	Body Text	•  Conflitos: Quando ambos os sistemas modificam o mesmo dado
341	Body Text	•  Performance: Sincronização não deve bloquear operações normais
342	Body Text	
343	Body Text	Estratégias comuns:
344	Body Text	•  Polling: Sistema verifica periodicamente por mudanças
345	Body Text	•  Webhooks: Sistema receptor é notificado de mudanças
346	Body Text	•  ETL: Extração, transformação, carregamento de dados

1908	Heading 2	Sincronização com Estados Inesperados
1909	Body Text	
1910	Body Text	Problema: WordPress API às vezes retorna dados incompletos ou inesperados (HTTP 400, timeout).
1911	Body Text	
1912	Body Text	Erros observados:
1913	Body Text	400 Bad Request - campos faltam
1914	Body Text	401 Unauthorized - credenciais expiradas  
1915	Body Text	429 Too Many Requests - rate limiting
1916	Body Text	504 Gateway Timeout - WordPress offline
1917	Body Text	
1918	Body Text	Solução Implementada:
1919	Body Text	
1920	Body Text	async function syncWithRetry(maxRetries = 3) {
1921	Body Text	  for (let attempt = 1; attempt <= maxRetries; attempt++) {
1922	Body Text	    try {
1923	Body Text	      const fichas = await wpClient.get('/wp-json/wp/v2/fichas');
1924	Body Text	      return fichas.data;
1925	Body Text	    } catch (error) {
1926	Body Text	      console.warn(Tentativa ${attempt} falhou:, error.message);
1927	Body Text	      
1928	Body Text	      if (error.response?.status === 401) {
1929	Body Text	        console.error('Credenciais WordPress inválidas - sincronização desativada');
1930	Body Text	        return [];
1931	Body Text	      }
1932	Body Text	      
1933	Body Text	      if (attempt < maxRetries) {
1934	Body Text	        const waitTime = Math.pow(2, attempt) * 1000; // Exponential backoff
1935	Body Text	        console.log(Aguardando ${waitTime}ms antes de repetir...);
1936	Body Text	        await new Promise(r => setTimeout(r, waitTime));
1937	Body Text	      }
1938	Body Text	    }
1939	Body Text	  }
1940	Body Text	  
1941	Body Text	  console.error('Sincronização falhou após todas as tentativas');
1942	Body Text	  return [];
1943	Body Text	}
1944	Body Text	
1945	Body Text	Resultado: Sistema é resiliente a falhas temporárias de WordPress.
