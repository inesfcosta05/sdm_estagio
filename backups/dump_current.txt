103	Normal	Este relatório apresenta o trabalho realizado no âmbito do projeto de estágio intitulado "Migração e Reestruturação de Plataforma de Gestão de Contactos", desenvolvido na empresa Celeuma Multimédia Lda entre fevereiro e junho de 2026.
104	Normal	
105	Normal	O projeto consistiu na modernização de uma plataforma existente baseada em WordPress, transformando-a numa aplicação web robusta e escalável utilizando um stack tecnológico moderno: React.js para frontend, Node.js/Express para backend, e MySQL para persistência de dados. A solução integra dados tanto da aplicação local como do WordPress, mantendo sincronização automática e garantindo compatibilidade com dados históricos.
106	Normal	
107	Normal	O trabalho foi organizado em fases: análise da arquitetura existente, levantamento de requisitos, design da nova arquitetura, implementação de backend e frontend, sincronização com WordPress, testes e deployment em ambiente local e de produção.
108	Normal	
109	Normal	A solução final implementa funcionalidades completas para gestão de fichas comerciais, clientes, páginas, perfis de utilizador, administração de acessos e relatórios, com interface intuitiva e consistente que privilegia a produtividade. O sistema implementa mecanismos avançados de adaptação dinâmica ao schema da base de dados, normalização de dados, sincronização incremental com WordPress e configuração por variáveis de ambiente.
110	Normal	
111	Normal	Os resultados demonstram uma melhoria significativa em termos de manutenibilidade, escalabilidade, coerência visual-funcional e experiência do utilizador comparativamente à solução anterior.
112	Normal	
113	Normal	Palavras-chave: Migração de plataformas, WordPress, React.js, Node.js, Arquitetura web, API REST, Sincronização de dados, Base de dados MySQL

120	Normal	This report presents the work carried out within the scope of the internship project titled "Migration and Restructuring of Contact Management Platform", developed at Celeuma Multimédia Lda between fevereiro e junho de 2026.
121	Normal	
122	Normal	The project consisted of modernizing an existing WordPress-based platform, transforming it into a robust and scalable web application using modern technology stack: React.js for frontend, Node.js/Express for backend, and MySQL for data persistence. The solution integrates data from both the local application and WordPress, maintaining automatic synchronization and ensuring compatibility with historical data.
123	Normal	
124	Normal	The work was organized in phases: analysis of existing architecture, requirements gathering, design of new architecture, backend and frontend implementation, WordPress synchronization, testing and deployment in local and production environments.
125	Normal	
126	Normal	The final solution implements complete features for managing commercial records, clients, pages, user profiles, access administration and reports, with an intuitive and consistent interface that prioritizes productivity. The system implements advanced mechanisms for dynamic adaptation to database schema, data normalization, incremental synchronization with WordPress and environment-based configuration.
127	Normal	
128	Normal	Results demonstrate significant improvement in terms of maintainability, scalability, visual-functional consistency and user experience compared to the previous solution.
129	Normal	
130	Normal	Key-words: Platform migration, WordPress, React.js, Node.js, Web architecture, REST API, Data synchronization, MySQL database

236	Heading 2	Plataformas de Gestão de Contactos
237	Body Text	Plataformas de gestão de contactos (também designadas CRM - Customer Relationship Management - ou sistemas de gestão de relacionamento com clientes) são ferramentas críticas para organizações que necessitam de gerir grandes volumes de informação sobre clientes, propostas, transações e comunicações.
238	Body Text	
239	Body Text	Historicamente, estas plataformas evoluíram de sistemas monolíticos para arquiteturas distribuídas:
240	Body Text	
241	Body Text	•  Fase 1 (Sistemas Monolíticos): Aplicações tudo-em-um, tipicamente desktop
242	Body Text	•  Fase 2 (Web Monolíticos): Aplicações web baseadas em templates server-side (PHP, ASP)
243	Body Text	•  Fase 3 (Separação Frontend/Backend): API REST com frontend separado
244	Body Text	•  Fase 4 (Microserviços e Cloud): Componentes independentes, escalabilidade horizontal
245	Body Text	
246	Body Text	A Celeuma operava entre as Fases 2 e 3, com WordPress (Fase 2) como base mas com necessidade clara de evoluir para Fase 3.

251	Heading 2	Arquiteturas Web Separadas por Camadas
252	Body Text	A separação entre camadas (layered architecture) é um padrão amplamente aceito em engenharia de software que organiza a aplicação em:
253	Body Text	
254	Body Text	•  Camada de Apresentação (Frontend): Interface com o utilizador
255	Body Text	•  Camada de Lógica de Negócio (Backend): Processamento, validação, regras
256	Body Text	•  Camada de Persistência (Base de Dados): Armazenamento duradouro
257	Body Text	
258	Body Text	Vantagens:
259	Body Text	•  Manutenção independente de cada camada
260	Body Text	•  Reutilização da API por múltiplos clients
261	Body Text	•  Escalabilidade horizontal
262	Body Text	•  Facilita testes unitários e integração
263	Body Text	•  Flexibilidade tecnológica
264	Body Text	
265	Body Text	Esta arquitetura foi o modelo escolhido para o projeto, com React.js no frontend, Node.js/Express no backend e MySQL na camada de dados.
266	Heading 2	Wordpress como plataforma de Conteúdos
267	Body Text	WordPress é um Content Management System (CMS) muito popular, construído em PHP e MySQL. Inicialmente desenvolvido para blogging, evoluiu para plataforma robusta suportando:
268	Body Text	
269	Body Text	•  Extensão via plugins
270	Body Text	•  Tipos de conteúdo customizados
271	Body Text	•  REST API abrangente (desde versão 4.7)
272	Body Text	•  Ecossistema vasto de temas e extensões
273	Body Text	
274	Body Text	No contexto deste projeto, WordPress funciona como:
275	Body Text	•  Fonte de dados históricos: Dados de posts, clientes anteriores
276	Body Text	•  Sistema de referência: Validação de dados sincronizados
277	Body Text	•  Possível destino: Alguns dados criados localmente devem refletir em WordPress
278	Body Text	
279	Body Text	A integração com WordPress é complexa porque:
280	Body Text	•  Schema não é fixo (customizado com plugins)
281	Body Text	•  API tem limitações de autenticação e rate limiting
282	Body Text	•  Dados podem estar em formatos variados
283	Heading 2	APIs REST e Integração entre Sistemas
284	Body Text	REST (Representational State Transfer) é arquitetura para construir serviços web usando primitivos HTTP. Princípios:
285	Body Text	
286	Body Text	•  Identificadores de Recursos: URLs representam entidades (/fichas, /clientes)
287	Body Text	•  Operações Padrão: GET (ler), POST (criar), PUT (atualizar), DELETE (eliminar)
288	Body Text	•  Representações: Tipicamente JSON ou XML
289	Body Text	•  Stateless: Cada requisição é independente
290	Body Text	
291	Body Text	No projeto, a API REST expõe:
292	Body Text	•  Recursos principais: fichas, clientes, páginas, utilizadores
293	Body Text	•  Operações CRUD completas
294	Body Text	•  Filtros e paginação
295	Body Text	•  Autenticação via tokens
296	Body Text	
297	Body Text	A separação frontend/backend via REST API permite:
298	Body Text	•  Frontend focar em UI/UX
299	Body Text	•  Backend focar em lógica de negócio
300	Body Text	•  Fácil integração com outros sistemas
301	Heading 2	Frameworks Frontend Modernos
302	Body Text	React.js (desenvolvido pelo Facebook) é biblioteca JavaScript para construir interfaces:
303	Body Text	
304	Body Text	•  Componentes: Blocos reutilizáveis de UI
305	Body Text	•  Virtual DOM: Otimização de rendering
306	Body Text	•  JSX: Sintaxe que mistura JavaScript com HTML-like markup
307	Body Text	•  Hooks: Gerenciamento de estado e ciclo de vida
308	Body Text	•  Ecossistema: React Router (routing), Axios (HTTP), Bootstrap (styling)
309	Body Text	
310	Body Text	React foi escolhido porque:
311	Body Text	•  Comunidade grande e madura
312	Body Text	•  Ferramentas excelentes (Create React App)
313	Body Text	•  Componentes reutilizáveis simplificam desenvolvimento
314	Body Text	•  Performance satisfatória para aplicações administrativas
315	Body Text	•  Curva de aprendizagem razoável
316	Heading 2	Sincronização de Dados entre Sistemas
317	Body Text	
318	Body Text	Quando múltiplos sistemas armazenam dados relacionados, surge desafio de sincronização:
319	Body Text	
320	Body Text	•  Consistência Eventual: Dados sincronizam mas não instantaneamente
321	Body Text	•  Incrementais vs. Completas: Sincronizar apenas mudanças ou tudo
322	Body Text	•  Conflitos: Quando ambos os sistemas modificam o mesmo dado
323	Body Text	•  Performance: Sincronização não deve bloquear operações normais
324	Body Text	
325	Body Text	Estratégias comuns:
326	Body Text	•  Polling: Sistema verifica periodicamente por mudanças
327	Body Text	•  Webhooks: Sistema receptor é notificado de mudanças
328	Body Text	•  ETL: Extração, transformação, carregamento de dados
329	Body Text	
330	Body Text	O projeto utiliza polling com tracking de lastSync e incrementalidade com post_date_gmt.

1888	Heading 2	Sincronização com Estados Inesperados
1889	Body Text	
1890	Body Text	Problema: WordPress API às vezes retorna dados incompletos ou inesperados (HTTP 400, timeout).
1891	Body Text	
1892	Body Text	Erros observados:
1893	Body Text	400 Bad Request - campos faltam
1894	Body Text	401 Unauthorized - credenciais expiradas  
1895	Body Text	429 Too Many Requests - rate limiting
1896	Body Text	504 Gateway Timeout - WordPress offline
1897	Body Text	
1898	Body Text	Solução Implementada:
1899	Body Text	
1900	Body Text	async function syncWithRetry(maxRetries = 3) {
1901	Body Text	  for (let attempt = 1; attempt <= maxRetries; attempt++) {
1902	Body Text	    try {
1903	Body Text	      const fichas = await wpClient.get('/wp-json/wp/v2/fichas');
1904	Body Text	      return fichas.data;
1905	Body Text	    } catch (error) {
1906	Body Text	      console.warn(Tentativa ${attempt} falhou:, error.message);
1907	Body Text	      
1908	Body Text	      if (error.response?.status === 401) {
1909	Body Text	        console.error('Credenciais WordPress inválidas - sincronização desativada');
1910	Body Text	        return [];
1911	Body Text	      }
1912	Body Text	      
1913	Body Text	      if (attempt < maxRetries) {
1914	Body Text	        const waitTime = Math.pow(2, attempt) * 1000; // Exponential backoff
1915	Body Text	        console.log(Aguardando ${waitTime}ms antes de repetir...);
1916	Body Text	        await new Promise(r => setTimeout(r, waitTime));
1917	Body Text	      }
1918	Body Text	    }
1919	Body Text	  }
1920	Body Text	  
1921	Body Text	  console.error('Sincronização falhou após todas as tentativas');
1922	Body Text	  return [];
1923	Body Text	}
1924	Body Text	
1925	Body Text	Resultado: Sistema é resiliente a falhas temporárias de WordPress.
